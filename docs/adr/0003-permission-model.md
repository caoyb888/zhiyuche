# ADR-0003 权限模型：代码注册表 + 角色分配动作码

日期：2026-09-09 | 状态：已采纳

## 决策

- 权限点在代码中定义（`internal/perm/registry.go`），分两类：**菜单**（`system.user`，带路由与图标）与**动作**（`system:user:create`）。启动时同步到 `permissions` 表，便于查询与前端展示，但真相在代码里
- 角色只被分配**动作码**；菜单可见性按约定派生：叶子菜单 `a.b` 在用户持有 `a:b:view` 时可见，父菜单在任一子菜单可见时可见
- 后端每条路由声明所需动作码（`auth.Require("...")`）；前端从 `/auth/me` 拿到动作码集合控制按钮，从 `menus` 拿到可见菜单树
- 平台超级管理员（`users.is_super`）绕过所有检查；`perm.PlatformOnly` 中的码（租户管理）只有平台租户的角色可持有
- 每个租户自动拥有内置角色：租户管理员（全部非平台权限，每次启动同步）、车队管理员、审批人、财务、员工（仅创建时赋默认权限，之后由租户自行调整）
- 用户的权限快照（含状态）缓存在 Redis 5 分钟；角色权限变化、用户停用、密码重置时主动失效，停用/删除同时吊销 refresh token

## 理由

菜单和按钮的权限只有一处定义，新增功能时只需在注册表加一行并在路由上声明；避免了"菜单权限表"和"接口权限表"两套数据漂移。
