# ADR-0001 后端采用 Go 模块化单体而非微服务

日期：2026-09-09 | 状态：已采纳

## 背景

技术方案 V1.1 规划了 10 个 Go 微服务（认证、卡务、计费、车辆状态、行程、账单、维保、通知、审批、充电）。项目起点是 6 辆车、单一园区，团队 2～3 人。

## 决策

V1 用**一个 Go 服务（`cmd/api`）承载全部业务模块**，按方案的服务边界划分为 `internal/<module>` 包；模块之间只通过 Go 接口调用，不共享表（每个模块只写自己的表，跨模块读通过对方的 service 方法）。

IoT 接入（`cmd/iot`）与 OCPP 充电桩接入（`cmd/ocpp`）因为是长连接协议服务，独立为进程，通过 NATS 与主服务解耦；定时任务独立为 `cmd/worker`。所有进程共用一个代码库、一个 go.mod。

## 理由

- 20 辆车以内的负载一个进程绰绰有余；微服务带来的部署、链路追踪、分布式事务成本在此阶段是纯开销
- 模块边界在包级别保持清晰，后续任一模块可原样抽成独立服务（Register 函数 + 自己的表 + 自己的 service）
- 单一进程便于本地开发与远程编译机上的联调

## 后果

- 需要纪律：模块不得直接 `JOIN` 其他模块的表；例外仅限只读的展示字段（如用户表 JOIN 部门名）
- 数据库仍是单库单 schema，多租户靠 `tenant_id` 行级过滤；SaaS 化时再评估 schema 隔离
